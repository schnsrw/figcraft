Why a fork The short version

Same editor. A cloud platform around it.

FigCraft is a great design editor that runs on your machine. FigCraft Cloud makes it something a whole company can run, sign in to and trust with its files, without changing the editor underneath.

What upstream FigCraft is.

An open-source, clean-room Rust reimplementation of the modern interface-design workflow, native first, that also runs in the browser through WebAssembly.

Its collaboration is a first preview: live sessions hosted from the desktop app, or a self-hosted figcraft-server that keeps a team's files on disk and hands out share links. That design is right for a native-first editor and small self-hosted teams.

"…has only a first preview of multiplayer (live sessions hosted from the app or a self-hosted server, with per-person undo and share links to edit or to view; no accounts, teams or cloud yet)…"

Upstream FigCraft README, Status section (docs/UPSTREAM-README.md)

What a hosted product needs on top.

A company running one design service for many people, or many organizations, needs a different set of guarantees. The architecture review puts it plainly: one data-directory lock, in-process room ownership and filesystem metadata are fine for self-hosting, but prevent horizontal SaaS scaling.

Durable edit history

An ordered event log in a transactional database, with sequence numbers, checksums and fencing, instead of files on one disk.

Object storage

Snapshots, images, libraries, plugins and exports as verified, immutable objects in any S3-compatible store.

Accounts and SSO

OIDC and SAML sign-in, browser sessions, service accounts and a bootstrap administrator, not just links.

Permissions

Tenant, team, workspace and document roles, deny by default, with revocation that ends live sessions.

Tenancy isolation

Many organizations in one deployment, isolated by row-level security and tenant-scoped keys.

Embedding and operations

Signed embed tokens for host products, plus quotas, backups, observability and rolling releases.

That is a different product with different trade-offs from a native-first editor. It belongs in a fork, so upstream can stay focused on the editor and the fork can take on servers, databases and accounts.

Add around the editor, never through it.

The fork's rules are written down as architecture decisions in docs/saas/README.md. These are the ones that keep it close to upstream.

Unchanged from upstream

  • The editor, renderer and command model, running locally in every client
  • The collaboration protocol and its per-person undo
  • The desktop app, the CLI and the filesystem figcraft-server

Added by FigCraft Cloud

  • apps/figcraft-cloud: one binary with api, relay and worker roles
  • crates/cloud-*: storage, relay, auth and domain crates
  • webapp/, deploy/saas/ and docs/saas/
SAAS-ADR-001

Keep the engine in the client

The Rust engine and renderer stay in clients, so editing remains responsive and offline-capable. The server never becomes a remote-rendered editor.

SAAS-ADR-013

Additive directories and adapter seams

Fork-owned work lives in its own directories, so regular upstream merges do not keep conflicting with editor files.

SAAS-ADR-003

Keep the filesystem server

figcraft-server remains the low-dependency option for offline and small-team users.

SAAS-ADR-004 to 008

Durability first

PostgreSQL is the source of truth, objects go to S3-compatible storage, Redis holds only rebuildable state, and one fenced relay owns each document at a time.

Upstream keeps flowing in.

The fork is only worth having if it keeps getting upstream's editor improvements. The sync policy makes that routine.

  • Fetch upstream at least weekly during active development, and integrate security fixes promptly.
  • Merge commits, never rebases, so each sync records the exact upstream boundary.
  • A patch ledger lists every change the fork makes to an upstream-owned file.
  • One sync, one merge: upstream merges are never mixed with feature work.
  • Upstream checks and cloud checks both pass before a sync lands.
